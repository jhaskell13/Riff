# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Riff is a **local music scene app** (Laravel 13, Inertia v3, Vue 3, Quasar + Tailwind 4, Vite 8, Leaflet): open it in a town and see the scene there — artists, shows, venues, bands looking for members — then become a fan of an artist and use their page to hear from them, talk with other fans, and support them. The map is the front door. Users hold multiple "artist identities" (band/solo/producer) via the `artist_user` pivot. ROADMAP.md is the source of truth for identity, principles, vocabulary (scene, fan, show, venue, listing) and phases — Phases 0 (dependable prototype), 1 (local discovery MVP) and 2 (the whole scene on the map: public artist pages, venues, shows, one combined scene map, scene views, listings) are complete; **Phase 3 (the artist page as the fans' home) is complete** — all eight steps, see docs/phase-3-plan.md: support links and fan counts, explicit post authorship, the fan wall and replies, artist-level moderation, show threads, "your scene", in-app notifications, and the weekly email digest. **Phase 4 (scene tools for members/venues/promoters) is next**, then Phase 5 (listening parties and live sessions, long-term).

**Product guardrails** (from ROADMAP's principles — check new features against them):
- Everything is anchored to a place, an artist, a show, or a venue. Do not add global timelines, algorithmic feeds, or popularity-only ranking. **`/scene` ("your scene", `YourSceneController`) is the signed-in home** and holds the nav slot the feed used to; the global `/feed` survives at the *end* of the nav as scaffolding for a future followed-entity digest (owner decision, November 2026) and must not be extended in its current form. Walls, threads and the home page are ordered by time and distance — never by likes.
- Fan interaction lives on the artist's page, where members speak *as the artist* and moderate their own wall. **Artists hide; only platform moderators remove.** Every artist-level action is reversible and appended to a trail (see Artist walls); an artist who wants something off Riff reports it, so a second person decides.
- Support links send money to where artists already get paid; Riff does not process payments until the Phase 4 decision gate.
- Public locations are approximate and chosen. Venues are *recurring* places; a one-off backyard/park/house show keeps its own town-level location on the show and must never become a venue row. Private venues (DIY by default) store no street address at all; listener locations are never public. Every new surface is reportable through `POST /reports`.

## Commands

```bash
composer run dev          # serve + queue listener + pail logs + vite, concurrently
composer test             # config:clear + full PHPUnit suite (offline; all HTTP faked)
composer analyse          # PHPStan (larastan), level 6 — CI enforces a clean run
composer check            # pint --test + analyse + test, i.e. what CI's quality gate runs
php artisan test --filter test_name_or_class   # single test
./vendor/bin/pint         # format PHP (CI enforces pint --test)
npm run build             # Vite build (client + SSR); REQUIRED before php artisan test
                          # if you added/renamed a page component (manifest check)
php artisan migrate:fresh --seed   # rebuild DB: pilot scene + ~75 scattered artists
php artisan riff:seed-pilot        # add just the pilot scene to an existing DB (idempotent)
php artisan riff:geocode-missing   # queue geocoding for records without lat/lng
php artisan riff:moderator a@b.com [--revoke]   # the only way to grant moderator access
php artisan riff:sync-places        # create/refresh scene places from stored town coordinates
```

Local default is SQLite; queue/cache/session use the database drivers. Test user from the seeder: `test@example.com` / `password` (a moderator locally). Cover art is written to the media disk, so `php artisan storage:link` is needed once or seeded photos 404.

**Seeded data** is the recruiting demo, and since November 2026 it seeds **real, already-public information** about the real Connecticut scene (owner decision): `database/seeders/data/pilot-scene.json` (via `Database\Seeders\Support\PilotScene`) carries real acts with their publicly credited **members**, factual bios built from public sources, their own Bandcamp links, and real venues at their public street addresses — plus fictional entries that still carry every *judgement* (the report queue, hidden/archived profiles, a cancellation, a declined slot), because being reported is not a public fact. Walls and show threads carry **simulated conversation, including words in the voice of real acts** — that is what makes the demo show a populated scene, and it is the one thing invented about a real subject.

**The hard line, enforced by `PilotDatasetTest`: no contact details, ever.** No email, phone or private address in the file; every seeded account is on an RFC-reserved `example.*` domain (`UserFactory::safeEmail`), so **a demo digest or notification cannot reach a real person's inbox** — which is the entire reason the rule exists. Also enforced: a real act's links must be their own pages, an invented act's must point somewhere nobody could own, and **no real DIY space is ever listed** (a club's address is public; a DIY space's is not). `DatabaseSeeder` runs the moderator account, `PilotSeeder` (acts, walls, moderation demo), `SceneSeeder` (venues/shows/listings/threads + `riff:sync-places`), then ~75 invented scattered artists. Demo and local dev only — the seeders refuse production, and none of it may ever reach a live database.

## Architecture

**Request flow:** routes/web.php → controller → Inertia::render('Dir/Page') → `resources/js/pages/Dir/Page.vue` (lowercase `pages/` — Inertia v3 convention; `Components/` and `Layouts/` are capitalized). Everything except `/` (redirects to the map), `/health`, auth routes, the public map routes (`map/artists`, `map/artists/{artist}`, `map/shows`, `map/venues`, `map/listings`, `map/places`), the public artist profile (`artists/{artist:slug}` plus the numeric-id redirect), the public venue page (`venues/{venue:slug}`), the public show page (`shows/{show}`), the public listing page (`listings/{listing}`), and scene pages (`scenes/{place}/{family?}`), all on the `map` limiter, sits behind `['auth', 'verified']` — User implements `MustVerifyEmail`, so verification is enforced for real.

**Authorization is policy-only.** `ArtistPolicy`, `VenuePolicy`, `ShowPolicy`, `LineupEntryPolicy`, `ListingPolicy`, and `LiveStreamPolicy` (auto-discovered) gate every state-changing route via `$this->authorize()` in controllers; the base `Controller` has `AuthorizesRequests`. FormRequests validate only (`authorize()` returns true). Artist membership = `User::isMemberOf()` (an `exists()` query). "Delete" of an artist is a soft-delete archive — shared identities must be recoverable.

**Geocoding pipeline (the part that spans files):** `User`, `Artist`, `Venue`, and `Listing` implement `App\Contracts\Geocodable` and are observed by `GeocodableObserver` (registered via `#[ObservedBy]` on the models). Creating a record without coords, or changing address fields, queues `App\Jobs\GeocodeAddress`, which calls `App\Services\Geocoder` and writes lat/lng via `saveQuietly()` (so observers don't loop). Geocoder returns `?MapPoint` — null means "couldn't geocode"; callers must treat null as "off the map", never substitute fake coordinates. Nothing in a request path ever geocodes. Geocoding is town-level for everything except a *public* venue, whose `geocodableAddress()` appends the street as a fourth component (`Geocoder::fromAddress(..., $street)`).

**Map:** `MapController@index` renders the shell with a center, `filterOptions` and `canFollow`. The shell and its data endpoints are all **public** and rate-limited (`map` limiter): `GET /map/artists`, `GET /map/artists/{artist}` (card), `GET /map/shows`, `GET /map/venues`, `GET /map/listings`, `GET /map/places?q=` (towns that have artists, using stored coordinates — never geocodes). `MapArtistsRequest` validates and normalises parameters into an `App\DTO\MapFilters` (bounds snapped outward via `Geo::snapBounds`, origin rounded to 3 dp, lists sorted, genre slugs → ids via the cached `GenreCatalog`); a request must give a viewport, a radius (`lat`/`lng`/`radius`/`unit`), or `q`. `App\Services\Map\ArtistMapSearch` does the work:
- Probes for row `cap+1` (not `COUNT`) to choose the shape. At or under the cap → all markers, nearest first. Over it → server-side grid clusters (`GROUP BY` cell, which also yields the total) plus the nearest `list_limit` via an expanding circle (exact: anything outside a circle holding ≥N is farther). Search-only (`q`, no area) is global and capped at `search_limit`.
- Distance in SQL is an arithmetic-only equirectangular expression (portable, orderable); display distance is haversine in PHP. Text search unions the name/hometown scan with a pivot lookup for matching genres — `OR` there was ~7× slower.
- Everything runs off the covering `artists_map_index (show_on_map, deleted_at, lat, lng)`. Keep new filters index-friendly, and benchmark against a large dataset before adding anything that reads table rows per match.
- **Shows, venues and listings** (`GET /map/shows`, `GET /map/venues`, `GET /map/listings`, `MapSceneRequest` → `App\DTO\SceneFilters` → `App\Services\Map\SceneMapSearch`) are drawn on the same map. All three requests share area parsing via the `ParsesMapArea` trait and `Geo::confine`. Shows: date window via `App\Support\ShowWindow` (tonight/weekend/week/month, in the viewer's `tz`), placed at `coalesce(venues.lat, shows.lat)` over a left join to non-deleted venues, genre = a *confirmed* act has it, hidden for a blocking viewer only when every confirmed Riff act is blocked. Venues: `show_on_map`, geolocated, dormant ones (no show and not added within `riff.map.venue_dormant_days`) fade; with genres, only venues with a matching bill coming up. Listings: `Listing::active()`, genre via `listing_genre`, a blocked artist's listings hidden. All three return a capped nearest-first list (`riff.map.max_scene_markers`) that the browser clusters — no server grid. Artist-only filters and the name search don't apply to them; they always follow the viewport.
- **SQLite gotcha (cost a debugging session):** PDO binds PHP floats as *strings*. Against a plain column SQLite converts them (numeric affinity); against an expression (`coalesce(...)`, the equirectangular distance) it does not, and a number never compares equal-or-greater to text — so the comparison silently fails (or, for `<=`, always passes). Compare expressions to `(? * 1.0)`, which is numeric on all three drivers. Likewise bind datetimes as `toDateTimeString()`, not Carbon objects, when the column is compared in a raw/`whereBetween` (an immutable Carbon can bind as ISO-8601, which SQLite compares as text).
- Non-personal results (all kinds) are cached under one `MapCache::version()`, rotated by Artist, Venue, Show, LineupEntry and Listing `saved/deleted(/restored)` and by `GeocodeAddress` for everything except users (it writes quietly). Anything that changes what the map shows without a model event must call `MapCache::bump()` — or `touch()` the artist, as genre-only edits do.

**Map UI** (`pages/Map/Index.vue` + `Components/Map/*`, `Composables/useMapData.js`, `useMapFilters.js`): the page owns the Leaflet instance; everything else is a component fed by it. Filter state lives in `useMapFilters` (including `kinds` — artists/shows/venues/listings, all on by default, shown on wide screens as one dropdown pill — and the shows' `when` window; `toQuery()` is the artists query, `toSceneQuery()` the shows/venues one) and is mirrored to the URL with `replaceState` (never `push` — panning would flood history). `useMapData`'s `useMapFeed(routeName)` (one per kind) debounces and aborts; an `AbortError` is not an error state, and a kind switched off is `clear()`ed, never left loading. Each kind (artists, shows, venues, listings) has its own markercluster group so clusters never mix kinds, and its own colour *and shape* on pins and bubbles (teardrop/round, calendar tile/rounded square, hexagon, speech bubble) plus a **fixed quadrant slot** around its point (`KIND_SLOTS` in markers.js) so different kinds at one point never stack. Kind CSS variants must come *after* the base `.riff-pin`/`.riff-cluster` rules (equal specificity — order decides; they once came first and every cluster rendered red). The list panel is full-width underlined tabs, one per kind switched on; shows/venues are diffed by `syncPlaces` keyed `kind:id`, and a selected one opens `PlaceCardPanel` from its pin payload. Markers and server clusters both render as the same `.riff-pin` / `.riff-cluster` divIcons built in `Components/Map/markers.js` — built with `textContent`, never HTML strings, because artist names are user input. Browser-side markercluster reuses `clusterIcon` so client and server grouping look identical. While a search term is active the client **omits bounds** so the search is global, and fits the map to the results once per term. Anything that visits/posts from the map must pass `preserveState: true`, or the Leaflet instance is torn down and rebuilt.

Leaflet popups, where still used, are built with DOM nodes (`textContent`), never HTML strings.

**Onboarding:** there is no landing page — `/` redirects to the map, and a first-time *guest* meets `Components/Map/WelcomeOverlay.vue` over it (auto-opened once from `Map/Index.vue`, remembered in `localStorage` under `riff.onboarding.seen`, reopenable from the FilterBar's help button; suppressed when the URL carries a view or filters, so a shared link is never covered). It offers the two paths Riff has: listener and artist. Each links to `register?intent=fan|artist`, normalised by `App\Support\OnboardingIntent` and stored on `users.onboarding_intent`. It lives on the user, not the session, because artist creation sits behind email verification and the verification link is routinely opened in another browser: `VerifyEmailController` resumes the artist path (sending them to `artists.create` when they still have no identity) instead of dropping them on the map. Keep both guest call-to-actions — the empty-map invitation and the card's Follow button — pointed at registration with the matching intent.

**Safety and moderation** — three separate things, deliberately:
- **Reporting** is one endpoint, `POST /reports` (`reports` limiter, the tightest in the app), taking a subject as `type`+`id` so the map card, artist/venue/show/listing pages, and the feed all raise reports the same way; the kinds live in `ReportStoreRequest::SUBJECTS` and the reasons in `config('riff.moderation.reasons')` (shared to the client as `reportReasons`, so the form can't offer what validation rejects). A report is built field by field, never mass-assigned — a request that could set `status` or `resolved_by_id` would let a reporter close their own report. A second open report on the same subject by the same person is silently not queued.
- **Blocking** (`artist_blocks`, mirroring `artist_follows`) is one listener's own view: the artist leaves *their* map and feed, is told nothing, and stays on everyone else's map. `MapFilters::hiddenFor` is set only when the viewer actually blocks someone (`User::hasBlocks()`), because it makes results personal and therefore uncacheable; everyone else keeps the shared cache. The exclusion lives in `ArtistMapSearch::matching()`, so markers, the nearest list, and cluster counts all agree. In the feed, the `NOT IN` must be ORed with `whereNull('artist_id')` or artist-less posts vanish (a comparison with NULL is never true). Blocking also drops the follow; `ArtistPolicy::block` refuses members their own artist. The only way back is the list in profile settings.
- **Moderation** is `users.is_moderator` — not fillable, no form, granted only by `riff:moderator` — read in exactly one place, `ReportPolicy`. `/moderation` is the whole surface: the queue (open oldest-first, settled newest-first) and one `POST` per decision. The decisions (dismiss, hide/archive artist, remove post, hide/archive venue, remove show, remove listing) are `App\Support\ModerationAction`, which also says which apply to which subject (`optionsFor()` feeds the buttons; the request re-checks). Nothing is destructive — hide takes the pin off the map, archive is the members' own recoverable soft delete, a removed post keeps its row. Resolving one report closes every other open report about the same subject, and `resolution`/`resolved_by_id`/`resolved_at`/`moderator_note` are the audit trail. `Report::reportable()` is `withTrashed()` so a report about an archived artist stays readable.

**Events:** `App\Contracts\EventProvider` → `App\Services\Events\TicketmasterEvents` (bound in AppServiceProvider), returning provider-agnostic `App\DTO\LocalEvent`s. Not wired to the UI yet. In Phase 2, artist/venue-submitted shows are the primary source; providers (local-first ones via this contract, Ticketmaster only as filler) are always labelled as imported and never outrank artist-confirmed shows.

**Notifications** (`notifications` table, `App\Support\NotificationType`, `App\Notifications\*`, `App\Services\Notifier`): in-app only so far — the email digest is step 8. Laravel's standard notifications shape, deliberately unmodified, because in-app messaging (Phase 4) will write to the same table. **Every send goes through `Notifier::send()`**, which asks the three questions that must not be forgotten: does this person want the kind (`users.notification_preferences`, a JSON map defaulting from `config('riff.notifications.types')`), have they **blocked** the artist it is about (blocking must not be walked through by a notification), and is it already in their bell. It also **drops the actor** — notifications carry `causedBy($user)` so no trigger has to remember not to tell someone about their own action; a trigger that calls `$user->notify()` directly skips all of it. **Folding:** a `collapseKey()` merges into an *unread* notification about the same thing inside `collapse_window_minutes`, bumping `data.count` — five posts from one band in an afternoon is one line, which is what keeps the bell from being the feed this product refuses to have. Per-artist mutes live on `artist_follows.notify` (`artists.follow.notify`), and apply only to kinds whose `respectsArtistMute()` is true: a reply to your own words is not a subscription. `lineup_invite` is marked `required` and cannot be switched off — an unanswered invitation keeps somebody else's show off every public surface, which is the Phase 2 debt this step pays. The unread count is shared lazily from `HandleInertiaRequests`; reads are scoped through `$user->notifications()`, never by id, so no route reaches another person's bell. **Seeders must pass `immediately: true`** — notifications are `ShouldQueue` and the local queue is the database driver with no worker, so a seeded bell would otherwise be five rows in `jobs`.

**The weekly digest** (`App\Services\WeeklyDigest` builds it, `App\Services\DigestSender` decides who gets one, `riff:send-digests` runs weekly from routes/console.php): "your scene, by email" — the shows you said you were going to first, then when the artists you follow next play, what they said since your last digest, and what's on around you. Three rules live in `DigestSender`: **only people who asked** (`users.digest_frequency`, and a verified address), **never twice inside `min_days_between`** (`digest_sent_at` is the cap, so a doubled scheduler or a hand-run command cannot write twice), and **never an empty one** — a person with no news is skipped *and their `digest_sent_at` is left alone*, so their window keeps growing until there is something worth sending. It uses `get()`, not `each()`/`chunk()`: sending updates the very column the query filters on, and chunking a shifting set silently skipped people. **Unsubscribe is a signed link that works signed-out** — requiring a login to stop email is how complaints become spam reports — and it only sets `digest_frequency = off`, touching nothing else. The HTML view escapes everything (**plain HTML, never a markdown mailable**); the `text/plain` view deliberately does *not* escape, because there is no HTML context there and Blade's default put `&amp;` in front of real band names. The lineup invitation is the **only** per-event email (owner decision 5).

**Your scene** (`/scene` -> `App\Services\YourScene` -> `pages/Scene/Home.vue`): the signed-in home. Two halves - the artists you follow (their **artist-voice posts only**, and when they next play) and your area (what's on and who's looking, whoever is playing). The "around you" half is composed from `SceneMapSearch` exactly as `SceneView` does, so the home page and the map can't disagree about "upcoming" or "blocked". **Per-viewer, therefore uncached** (the `MapFilters::hiddenFor` rule) - which makes bounding it the only protection it has: every section has a hard limit from `config('riff.scene_home')` and the updates paginate. Pulling *fan* posts off followed walls would turn it back into the stream of strangers it replaced, so it doesn't. Tests assert the ordering is date/distance and that query count doesn't grow with the follow list.

**Show threads** (`pages/Shows/Show.vue` → `Components/Wall/ShowThread.vue`): the same comments, replies, likes, indentation, hiding and reporting as a wall, on a `Show` instead of a `Post` — this is what the polymorphic comments were for, and there is no second implementation. A show gets **one flat thread**, not a wall of posts. `POST shows/{show}/comments` writes it, `GET shows/{show}/comments` pages it (public, `map` limiter), and `CommentThread` takes a `replyRoute` prop so replies land on the right endpoint. The thread **closes** `config('riff.shows.thread_closes_after_hours')` (24) after the start, and on cancellation — read-only, never deleted, because what was said still explains the night. Owned by the **host artist** for *moderation*, but **open to any verified user** for posting: a show is a public event, not the host's page, so `commentsFollowWallMode()` is false for a `Show` and a follow is not required to ask about the door time. Bans and blocks still apply. Speaking *as* an artist is granted by `Commentable::voiceArtistFor()` - the host **or any confirmed act on the bill** the user belongs to (pending acts have no standing, since they appear on no public surface). Posting in a thread never creates an RSVP, and the thread is not a back door to private attendees (both tested).

**Walls:** `pages/ArtistZone/Show.vue` renders `Components/Wall/*` — `ArtistWall` (composer, stream, and the members' ban list), `WallComposer` (the voice toggle, shown only to members, defaulting to the artist's voice on their own page), `WallPost`, and `CommentThread` (self-referencing, but only one level deep, and visibly indented behind a rail). The wall is the **last** card on the page: it grows without bound, so everything factual about an artist reads before it. Posting, commenting, reacting and moderating all `preserveScroll`. "Show more comments" / "See more replies" fetch `wall.comments.index` / `wall.replies.index` with global axios and append client-side, **starting from page 1 and deduplicating by id** — the endpoints page by `comments_per_page`, not by the handful the wall shipped, so asking for "page 2" would silently skip everything between.

**Known prototype (do not polish):** livestreaming transport — HTTP POSTed base64 chunks re-broadcast over *public* channels — is a dead end, to be retired and replaced by a managed provider for Phase 5 "sessions". Its endpoints are policy-protected; leave the transport alone. The dormant like/comment schema shipped in Phase 3 as artist-page walls and replies (see Artist walls below).

## Conventions and gotchas

- Persist only `$request->validated()`; create user-owned rows through relations (`$request->user()->posts()->create(...)`) so ownership can't be mass-assigned. MassAssignmentTest enforces this.
- Tests must be environment-independent: external HTTP via `Http::fake()`, broadcasts via `Event::fake()`/pinned null driver. phpunit.xml pins `BROADCAST_CONNECTION`, empty `GOOGLE_MAPS_API_KEY`/`TICKETMASTER_API_KEY`; add a pin there when introducing any env-dependent service.
- Column naming is inconsistent by history: artists use `hometown`/`stateOrProvince`, users use `city`/`state`. `Geocodable::geocodableAddress()` papers over this.
- Feed posting is rate-limited via the named `posts` limiter (AppServiceProvider); following uses the `follows` limiter. Feed JSON goes through `PostResource` — extend the resource, don't serialize models raw.
- **Genres are a pivot, not a column.** `artists.genre` is gone; use the `genres`/`artist_genre` tables via `Artist::genres()`. The curated vocabulary lives in `config('riff.genres')` and is reconciled by `GenreSeeder` (idempotent). Values that aren't curated are flagged `is_curated = false` rather than dropped.
- **Playable music:** `artists.music_url` is set through an Eloquent `Attribute` that runs `App\Services\MusicLink::parse()`, storing the canonical URL and deriving `music_provider`. `music_provider` is not fillable. Embed URLs are rebuilt on read (`$artist->music_embed`) from fixed per-provider templates — never interpolate a user-supplied URL into an iframe `src`. Unrecognised links are rejected by `App\Rules\PlayableMusicUrl`.
- **Artist photos:** `artists.image_path` (not fillable; written only by the upload pipeline) on the `config('riff.media.disk')` disk; `image_url` is a read-only accessor that replaced the old column. Uploads must be re-encoded to strip EXIF — a phone photo's GPS tags would leak the location the public-area rule exists to protect. Requires the `gd` extension.
- **Support links** (`App\Models\ArtistSupportLink`, `artist_support_links`; types in `config('riff.support.types')`): typed link-outs to where an artist already gets paid. Riff handles no money and takes no cut, so **nothing here is ever embedded** — `App\Services\SupportLink::parse()` canonicalises, and the renderer pairs every link with `rel="noopener noreferrer nofollow"` and shows the host so nobody clicks blind. The parser refuses non-http(s) schemes, URLs carrying credentials (`https://bandcamp.com@evil.example` reads as Bandcamp and resolves elsewhere), non-public/IP/odd-port hosts, and interior control characters; surrounding whitespace is trimmed, since a trailing newline is a normal paste. Types with a `hosts` allowlist (`bandcamp`, `tip_jar`) must be on it — the ones where going elsewhere is a scam, not a typo; an empty list means any host, because a band's own shop is on its own domain. **There is deliberately no `url` mutator on the model**: canonicalising needs the sibling `type`, and `fill()` follows the incoming array's order, not `$fillable`'s — so it lives in `App\Services\ArtistSupportLinks::sync()`, which saves the whole section at once. That sync **matches kept rows by id to preserve their click counts**, and ignores any id not belonging to the artist (the form's ids are a matching hint, never an authorization boundary). `artist_id` and `clicks` are not fillable. Clicks are a **bare aggregate counter** bumped by a public, throttled `POST artists/{artist}/support/{link}/click` (204, beaconed via global axios, failure swallowed — counting a click must never interrupt one): no per-user rows exist to leak, and the count is never published (`SupportLinkResource::withClicks()` gates it to the edit page), because a public click count would be the popularity ranking principle 2 rules out.
- **Fan counts** (`App\Services\FanCounts`): counts only, never names or places. `local()` counts followers within `config('riff.fans.local_radius_km')` of the artist's own point using the map's arithmetic-only equirectangular distance with every bound value forced numeric (`? * 1.0`) — the SQLite float-against-expression trap, with a regression test asserting the circle isn't just its bounding box. Null (not 0) when the artist has no coordinates. `displayLocal()` returns `"< 5"` below `config('riff.fans.local_floor')`, since an exact small number beside a small town narrows a listener down. Cached per artist **keyed on its coordinates**, because the geocoder writes them with `saveQuietly()` and no model event would invalidate an id-only key; follow/unfollow call `forget()`.
- **Artist walls — posts and comments carry an explicit voice.** `App\Support\AuthorContext` (`artist` | `fan`) is stored on both `posts` and `comments`. The two axes are separate: `posts.artist_id` is the **wall** (whose page it appears on), `author_context` is the **voice**, `user_id` is **who typed it** — always recorded for the audit trail, and **never serialised when the voice is the artist's** (`PostResource`/`CommentResource` enforce it; a band speaks as the band). **The voice is resolved in exactly one place, `App\Services\Wall::voiceFor()`**, from the authorization result — never from the request. `author_context`/`artist_id` are fillable but are *never validation rules*, so `...validated()` can't carry them (the `status` precedent); `MassAssignmentTest` covers it. Who may post is `ArtistPolicy::postAsArtist` (membership) and `postOnWall` (`artists.wall_mode`: `fans` default | `everyone` opt-in | `members_only`; members always may, blockers never). Asking for the artist voice without membership is **refused**, not downgraded. Replies are **one level deep** (`CommentRequest` rejects a reply-to-a-reply, and a parent on another post). Comments are **polymorphic** (`commentable_type`/`commentable_id`) so Phase 3's show threads reuse them rather than giving every show a phantom post row. `comment` is in `ReportStoreRequest::SUBJECTS` and `ModerationAction::RemoveComment` sets `status = removed` (row kept, like a post).
  - **`posts.comments` was dropped** — it was an unmaintained integer counter column that *shadowed* the relation, so `$post->comments` returned `0` instead of the replies (eager loading worked, reading it did not). Exactly the `likes` trap. `likes` stays because `ReactionController` maintains it and its relation is `likers()`; comment counts come from `withCount()`.
  - **Never let the wall's per-row permissions hit the policies.** Every post and reply asks "can I delete / reply here?", which on one wall turns on two facts. `App\DTO\WallViewer` computes them once and is passed into the resources (`forViewer()`, the `withDistanceFrom()` precedent); reaction state is a `withExists('likers as is_liked')` in the wall query, never `isLikedBy()` per row. `WallTest` asserts the query count **does not grow** with wall contents (it was 42 vs 18 before). A memo on the `User` model was tried first and rejected: it went stale when a follow was written outside the follow controller.
  - Nested resource collections serialise as `{"data": [...]}` — wall children are mapped and `resolve()`d to plain arrays so the client isn't reaching through a wrapper.
  - **Badges say the author's standing, never repeat their name.** `App\DTO\ThreadBadges` emits `{label, tone}`: `Artist` / `Host` (the owner), `On the bill` (another confirmed act), `Member` / `Member of X` (someone in one of those bands posting as themselves). The author line already names who spoke, so the badge once showed the band's name twice in a row. Built **once per render** (`forWall()` for a wall, `for()` per thread) and resolves membership in a single `artist_user` query - building it per post was an N+1 the wall's query-count test caught.
  - **Reading a wall goes through `App\Services\WallReader`**, never a hand-rolled query: three callers (the page and the two thread endpoints) must agree, and *who sees hidden content* is one of the rules they must agree on. The status vocabulary and the visibility decision live in `App\Models\Concerns\HasWallStatus` as `visibleStatuses(bool $includeHidden)` — a plain list fed to `whereIn`, not a scope, because most of these queries are built inside eager-load closures where the receiver is a `Relation` and a scope resolves for neither the reader nor PHPStan.
- **`App\Contracts\Commentable`** is what keeps threads from branching on class. A wall post and a show both answer `comments()`, `moderatingArtist()`, `acceptsComments()` and `commentsClosedReason()`, so `CommentController`, `CommentPolicy::createOn`/`createAsArtistOn`, `WallReader` and `WallModerationController::wallOf()` ask the subject instead of running `instanceof` chains. **Both answers reduce to one idea: a thread belongs to an artist** — a wall post to the page's artist, a show to its host. Null from `moderatingArtist()` means "no thread here" (a wall-less legacy post, or an archived host) and must 404, never "open to everyone". Adding a commentable kind means implementing the contract, not finding every branch.
- **Artist-level moderation** (`App\Services\WallModeration`, `App\Support\WallAction`, `wall_moderation_events`, `artist_wall_bans`): members keep their own page tidy, gated by `ArtistPolicy::moderateWall` (membership). Three rules the service exists to hold in one place: **(1) artists hide, never destroy** — `status` flips to `hidden`, the row stays, and there is no artist-level route that deletes a fan's words (`wall.posts.destroy` answers only to the author); **(2) a moderator's `removed` outranks an artist's `hidden`** — unhide restores only what the artist hid, so a band can't undo a platform decision, and hide won't relabel a removed row as theirs; **(3) every action is appended to the trail**, never updated, so a row hidden → restored → hidden again reads as that. `moderationTrail` is emitted to members only (`WallReader::trailFor`), newest first. A **wall ban** stops someone posting but leaves their follow, their reading, and everything they already wrote — "stop posting here" and "take down what you said" are deliberately separate; a member can't be banned from their own wall. Members escalate to the platform with the same `POST /reports` everyone uses, and hiding something never closes a report about it.
- **Public slugs (artists, venues):** links are permanent, slugs follow the name. Models implement `App\Contracts\HasPublicSlug` and use the `App\Models\Concerns\HasHistoricalSlugs` trait (hooks call `App\Support\Slugs`; `slug` is never fillable): a rename parks the old slug in a per-model history table (`artist_slugs`, `venue_slugs`), where the trait's `resolveRouteBinding` still resolves it and the controller 301s to the canonical URL; renaming back reclaims it. Slugs are never all digits (the numeric `/artists/{id}` redirect would shadow them) or a reserved route word (`Slugs::RESERVED`: create/edit/new) — both get the model's `slugFallback()` suffix. Gotcha: the redirect route's parameter is `{artistId}`, not `{artist}` — Laravel strips binding fields from URIs, so `{artist}` and `{artist:slug}` would key as the same route and the later registration silently wins.
- **Venues** (`App\Models\Venue`): recurring places only, kinds/age policies in `config('riff.venues')`. `address_visibility` is `public` | `private`; the `saving` hook nulls `street_address` for private venues whatever the request sent, and `geocodableAttributes()` includes the visibility so going private re-geocodes at town level. Render addresses only via `public_address` / `VenueResource` — never build one from the columns. `show_on_map` and `submitted_by` are not fillable (a submitter can't undo a moderator's hide). Created through `$user->submittedVenues()`; one per name per town (case-insensitive `lower()` check, driver-portable). `venues` limiter is per-minute *and* per-day. Moderation: `hide_venue` (off the map, page stays) and `archive_venue` (soft delete, page 404s). On the map since Phase 2 Step 4 (see Map).
- **Shows** (`App\Models\Show`, `LineupEntry`, `show_rsvps`): a show is at a `venue_id` **or** a one-off location of its own (label + town + note, never a street, never a venue row) — the request enforces exactly one and the model's `saving` hook clears a venue show's location columns. `Show` is **not** on `GeocodableObserver`: it carries the same hooks itself, only for one-off locations (a venue show is placed by its venue). Times are UTC + the show's IANA `timezone`; always render via `localStart()`/`localDoors()` or `ShowCardResource`/`ShowResource`, never the raw UTC. `host_artist_id`, `created_by`, `source`, `cancelled_at` are not fillable. **Lineup consent lives in one place, `App\Services\Lineup::sync()`** — own artists confirmed, other Riff artists pending, material change (date/time/place) re-asks; never write `lineup_entries.status` elsewhere except the confirm/decline endpoints. Public surfaces use `confirmedLineup()` only. Listings chain `listed()` (not cancelled, host not archived) and `upcoming()`; inside `whereHas()` use `notOver()` (no ORDER BY in subqueries). Cancel (hosts) keeps the page; `remove_show` (moderators) soft-deletes. Lineup/venue pickers use `/search/artists|venues` (strip `%`/`_`, lower-cased LIKE — portable), not the map search, because hidden-from-map artists still play shows. Age policies are shared: `config('riff.age_policies')`.
- **Scenes** (`/scenes/{place}/{family?}`, `SceneController` → `App\Services\SceneView`): a `Place` plus an optional genre family from `config('riff.scenes.families')` (`App\Support\SceneFamilies`; families list genre *names*, every curated genre must be in one — `SceneTest` enforces it). `SceneView` composes `ArtistMapSearch` + `SceneMapSearch` with a radius (no viewport) — never reimplement scene rules separately; cached under `MapCache::version()` except for blocking viewers. `places` rows come only from stored town-level coordinates (artists, private venues, one-off shows — never public venues' street points), via `riff:sync-places` (scheduled daily in routes/console.php, run by seeders) and `Place::record()` in `GeocodeAddress` for artists; never geocoded, never deleted. Slugs are `Place::slugFor(city, region)` (deterministic). Link into a scene with `App\Support\SceneLinks::for()`, which returns nothing if the town has no place yet.
- **Listings** (`App\Models\Listing`, `ListingReply`; types/instruments in `config('riff.listings')`): `as_artist` per type decides required/never/optional, and the artist is set only after `ArtistPolicy::update`. `user_id`, `artist_id`, `expires_at`, `closed_at` are not fillable. Public surfaces use `Listing::active()` (open, unexpired, artist not archived); managers are the poster and the artist's members (`isManagedBy`, `managedBy` scope). Town-level geocoding via `GeocodableObserver`. Replies: one per person, contact required, relayed by `ListingReplyMail` — **plain HTML view, never markdown** (markdown mail would parse user text), **no Reply-To**, and in mail views never name a variable `$message` (Laravel reserves it for the Message — it silently clobbered the reply text).
- **Follows:** `artist_follows` pivot via `Artist::followers()` / `User::followedArtists()`. Counts come from `withCount('followers')`; deliberately no `followers_count` column, which would shadow the relation (same trap as `likes`).
- The map shell and its data endpoints are public and land signed-in users too: `/` redirects to `/map`, and every post-auth redirect goes to `map.index`. `AuthenticatedLayout` renders for guests (`auth.user` may be null) — guard anything account-specific.
- `show_on_map` lets an artist keep a public profile without a pin; every map query must chain the `visibleOnMap()` scope alongside `geolocated()`.
- Distances render in `users.distance_unit` ('mi'/'km'), guessed at registration by `User::distanceUnitForCountry()`.
- Like relations are named `likers()` (Post, Comment): the tables carry integer `likes` counter columns, and a relation named `likes` would be shadowed by the column.
- Archived artists can be restored: `artists.restore` route uses `->withTrashed()` binding and `ArtistPolicy::restore` (membership checked with trashed included). Coordinates are nulled the moment an address changes (observer `updating`) — stale map positions are a bug.
- CI (`.github/workflows/ci.yml`): a quality job (pint --test, PHPStan, composer validate + audit, npm audit) and a test matrix that runs the full suite **on SQLite, MySQL 8.4, and Postgres 16**, then seeds from scratch and re-runs the pilot seeder on each. Write driver-portable SQL: the matrix exists because SQLite silently accepted an unknown column as a string literal and an out-of-vocabulary enum value, both of which are hard errors on the real drivers. deploy.yml gates CodeDeploy to EC2 on CI, ships a per-commit bundle (`release-<sha>.zip`), and waits for the deployment to actually succeed. The CodeDeploy script builds production `.env` from `.env.example` + Secrets Manager; APP_KEY comes from the secret's `app_key` (or the previous release's .env) and `app_url` in the secret is required — the script refuses to deploy localhost as APP_URL.
- **Model strictness:** `Model::preventSilentlyDiscardingAttributes()` is on outside production (AppServiceProvider), so passing a non-fillable field to `create()`/`fill()` throws instead of vanishing — that silence is how a fixture once set `lineup_entries.status`, had it ignored, and asserted the opposite of what it claimed. The other two halves of `shouldBeStrict()` are deliberately off: `preventAccessingMissingAttributes` fails 18 tests (models serialised after a narrowed `select`, as Inertia does with the auth user) and `preventLazyLoading` many more. Both are worth adopting on their own branch — see docs/audit-2026-11.md.
- **Security headers** come from `App\Http\Middleware\SecurityHeaders` (appended to the `web` group): `X-Frame-Options`, `X-Content-Type-Options`, `Referrer-Policy`, `Permissions-Policy`. There is deliberately **no CSP** — Riff embeds third-party players, loads map tiles from a provider and serves a Vite bundle, and a wrong CSP breaks the map silently.
- **Counters move only when the database says a row changed.** `ReactionController` uses `insertOrIgnore` on the likes pivot and increments on an affected-row count of 1; `detach()`'s return value guards the decrement. An `exists()`-then-`attach()` pair is a read-then-write that two concurrent taps both pass, and the second 500s on the unique index. Same shape in `DigestSender`: the weekly slot is **claimed with a conditional `UPDATE`**, so two overlapping runs cannot both email one person.
- Static analysis is Larastan at level 6 (`phpstan.neon`), with generics/iterable-docblock pedantry and the nullsafe-before-`??` style rule ignored. Models carry `@property` docblocks (above the `#[ObservedBy]` attributes — below them PHPStan ignores the block); keep them current when adding columns or accessors.
- Tailwind 4 is CSS-first: design tokens live in `@theme` inside resources/css/app.css (no tailwind.config.js); plugins load via `@plugin`, extra scan paths via `@source`. The `@tailwindcss/vite` plugin replaces PostCSS.
- **CSS cascade layers (read before adding any stylesheet).** Tailwind v4 emits everything inside `@layer`s, and unlayered CSS beats *all* layered CSS regardless of specificity or order. The order is declared once at the top of app.css: `properties, theme, base, quasar, vendor, components, utilities, quasar-restore`. Quasar loads via `resources/css/quasar.sass` (wraps it in `@layer quasar`; the Quasar plugin still injects `quasar-variables.sass`), its icon font via `resources/css/icons.css`, Leaflet + markercluster via `resources/css/map-vendor.css` (`layer(vendor)`). **Never import third-party CSS unlayered** — it silently overrides Quasar and Tailwind (it already did: Leaflet's `#ddd` background, Material Icons un-hiding QTabs arrows). Scoped component styles are unlayered on purpose and win, which is what they're for.
- Tailwind utilities now beat Quasar. Where a Tailwind utility shares a name with a class Quasar's components emit but means something else, Quasar breaks: today only `.inline` and `.flex` (vs Quasar's `.row.inline`/`.flex.inline` = inline-flex), restored in the `quasar-restore` layer at the end of app.css. Re-check when adding Tailwind classes that look like Quasar's (`row`, `column`, `flex`, `inline`, …).
- Quasar fields on the dark surfaces need `dark` (and usually `label-color="grey-5"`) or their text and chips render dark-on-dark; `q-select` `use-chips` needs a `#selected-item` slot with explicit chip colours (the default chip was text-on-same-colour). Quasar's `p { margin-bottom: 16px }` still applies — add `m-0` where a paragraph is a single line in a tight stack.
- **Leaflet:** import it only from `@/Components/Map/leaflet` (default import + plugins). `import * as L from 'leaflet'` is a namespace *copy* in production builds, so `L.markerClusterGroup` (added to `window.L` by the plugin) is missing — the map worked under the Vite dev server and was blank after `npm run build`. Without `VITE_LEAFLET_JAWG_PROVIDER_KEY` the map runs tile-less with a notice instead of throwing.
- **Map markers are diffed, not rebuilt** (`drawMarkers` in Map/Index.vue): markercluster collapses an opened cluster on any add/remove, and nearly every pan re-fetches the same artists. Same-town clusters (identical coordinates — no zoom separates them) and clusters already at their bounds zoom open in place via `spiderfy()`; `zoomToBoundsOnClick` is off. The "you are here" halo is non-interactive and drawn *beneath* markers (`zIndexOffset: -10000`) so it never hides or swallows clicks for the artists at its centre.
- Quasar's vite plugin runs with `astAutoImport: false` (see vite.config.js) because its AST auto-import double-registers under Vite 8 and breaks the build with duplicate imports; revisit when the plugin supports Vite 8 cleanly.
- leaflet-providers v4 uses a single `Jawg` provider with a `variant` option (`jawg-dark`), not `Jawg.Dark`.
